# M5 Gate A: proposal and M4 compatibility inventory

**Status: proposal for owner review.** This document does not approve or implement an M5 algorithm, saved-world format, numerical contract, or acceptance result. Every proposed default and technique below is provisional. The owner has requested a finite-world proposal, a configurable human profile with a default standing height of **185 cm**, and configurable cave topology, sizes, pocket policy, protection, and flooding. The capsule radius, slope, step, and the other choices below remain open. A decision to explore a proposal is not approval to freeze its detailed byte encoding or algorithm.

## Existing compatibility boundary

This inventory describes the source at plugin revision `6adfaada528c7f648193c9c4c726541b6b63ae54`; it is not a new verification result.

- `FVoxelLandM4SavedWorld` contains a versioned, UObject-free snapshot and identity. It retains copied graph sources and function dependencies, cooked programs, overrides, baked curves and generation settings, not a transient prepass grid. Its property-serialized record is trusted input; callers must bound archive size before deserialization. See [M4 saved worlds](M4_Saved_World.md).
- `VoxelLandM4WorldIdentity` validates inputs and constructs canonical identity bytes with the program fingerprints and density-affecting settings. The M4 guide describes readable identity versions 1–6, the original comparison rules, and explicit rejection of unknown versions. Switching noise backend changes terrain and is not a compatible migration. Do not reinterpret an old record or overwrite its identity.
- `FVoxelLandProgramCodec` distinguishes source and program fingerprints and records function dependencies. Preserve this distinction from any proposed plan dependency key, plan hash and chunk hash. A cache hit cannot substitute for validating the complete current inputs and providers.
- `FVoxelLandGenerator` supports immutable M4 height data, optional height detail, overhang and density smoothing. M4 quantizes and saturates base samples to `int16` before Smooth Density; the filter operates after that conversion. A height grid alone is not proof of the final surface under those operations. Finite and erosion-disabled chunk-local generation have different domain contracts. M5 must neither alter the no-cave path nor substitute a different backend.
- The existing M4 saved-world path documents explicit asynchronous initialization and a data-only server intent; its return value means request admission rather than generation success. `BeginPlay` must remain inert. The existing plan requires world-local cancellation and stale-result protection for new M5 work.
- M4 was accepted by the owner based on their reported build/tests and working editor, game and 2 km inspection. Cooked-build, dedicated-server, cross-host, wider-world and documented multi-seed checks remain deferred; this document does not claim them as passed. No build or tests were run for this inventory.

## Decisions requested

The following is one coherent starting point, not a stable specification. Values are editable authoring defaults where indicated; validation must reject unsupported settings rather than silently clamp them. The eventual descriptor must include every value affecting density or plan selection.

| Area | Proposal for review | Tradeoff, limits, and decision needed |
|---|---|---|
| Planning coverage | Start with one explicit finite 3D plan volume, inheriting its horizontal bounds from the configured finite M4 world and using editable vertical bounds. Treat lower bounds as inclusive and upper bounds as exclusive. Require the complete entrance, roof, primitive, mesh, filter and validation footprints inside the upstream domain. Reject a plan that does not fit; do not silently clamp its bounds. Reject planned networks in chunk-local mode until a separately versioned regional portal and ownership design exists. | A bounded plan avoids inventing cross-region connectivity, but does not provide connected caves throughout a large local-mode world. The vertical preset, exact domain limits and halo must be derived after surface and numerical contracts are agreed. Is this initial coverage acceptable, and must local-mode noise pockets be supported in the first release? |
| Player envelope | Make standing height, radius, maximum floor slope, maximum step, clearance margin and validator tolerances an explicit configurable profile. Default standing height is **185 cm**. For discussion only, consider radius **35 cm**, slope **45°**, step **45 cm**, and clearance margin **10 cm**. | The proposed remaining values are **not approved** and must match the intended character/movement design. Define whether capsule height includes hemispherical ends, the entrance geometry and a conservative continuous sweep/error bound; unsupported or unproven geometry fails. What are the authoritative radius, slope, step and margins? M11 movement remains a later end-to-end check. |
| Surface and stage order | Consider evaluating the complete supported M4 base field, retaining its existing base-sample `int16` quantization and saturation and then its optional smoothing. Apply hard planned-cave subtraction and optional pocket subtraction with roof/protection rules, followed by a **second** post-carve conversion to stored density. Specify that second conversion's rounding, saturation and units independently before freezing the format; do not assume it duplicates the first conversion. Validate the resulting quantized, meshed representation with conservative bounds covering both conversions, the filter, and mesh and sample errors. Initially reject detail/overhang/filter combinations if their final-surface or roof safety cannot be proven. | This preserves the M4-only order but changes the enabled-M5 stage order, requiring a distinct identity and explicit filter/halo and both conversion semantics. A height lookup or ideal centerline alone cannot prove clearance or prevent openings. Should those combinations be rejected initially, or must the first release support them? What roof thickness and entrance margin are desired? |
| Topology and cave size | Offer configurable chamber count/density, tunnel and chamber dimensions, entrance count, loop count/probability and path shape. For discussion only, use **8–24 chambers**, **2 entrances**, **0–3 loops**, tunnel radius **250–400 cm**, and chamber radii **500–1000 cm**. Deterministically fail an impossible plan after a finite, configurable or versioned attempt budget; never drop connectivity silently. | These are unapproved visual starting points, not a walkability guarantee. Some combinations of count, radius, domain and capsule profile are invalid. Require every planned chamber, edge, junction and entrance to satisfy the selected profile; define loop construction, deterministic tie order and bounded repair before implementation. Are these ranges and the reject-after-budget policy suitable? |
| Pockets | Make pocket enablement, density/frequency, depth range and attachment/enclosed-void policy editable. Proposed default: **disabled** until enabled by the author; when enabled, allow attachment to a planned cave and enclosed voids, while making no connectivity or walkability promise for pockets. | Pockets must still obey roof and protection rules and may not invalidate guaranteed routes. Specify provider, coordinate precision, roof clearance, thresholds and exact semantics before enabling a saved format. Should both attached and enclosed pockets be independently selectable? |
| Protection and water | Accept an immutable protection input and an explicit authorable default. Proposed initial default protection is **unprotected**, with an optional constant or supplied mask; reject plans crossing protected solid. Make water policy and level configurable: for example, **ignore water**, **reject below-water entrances/cavities**, or **allow and mark flooded caves**. | Unprotected means no protection is inferred from future roads or POIs. Ignoring water is not a promise of dry caves or simulation; allowing flooding adds metadata, not fluid behavior. Define which policies are required at launch, mask units/interpolation/precedence, whether pockets may enter water, and the behavior when water data is unavailable. |
| Numeric identity and migration | Propose checked global integer centimetres for authoring positions, mathematical floor division for negative coordinates, fixed-width canonical little-endian encoding, separate seed namespaces for candidates/edges/entrances/noise, deterministic total ordering, and independent reference vectors. Retain M4 records and use a separate explicitly versioned M5 identity/descriptor if caves are enabled. | Centimetres do not establish safe coordinate ranges, intermediate widths, fractional geometry, unbiased sampling, PRNG choice, SDF approximation, rounding or cross-host parity. All require a written, independently checked contract before a stable version. Preserve old versions/backends or reject unavailable ones; migration must be explicit and retain the original record. Approve a detailed numeric/seed/geometry proposal and its bounded range before freezing. |
| Resources and lifecycle | Admit finite memory/work before dispatch; provisionally cap a single plan at **256 candidates, 32,640 candidate edges, 8,192 segments, 8 attempts, and 256 MiB of accounted scratch and immutable plan data**, with **one active producer per world**. Validation work also needs an explicit finite cap derived from its eventual algorithm. Use immutable snapshots and per-world cancellation; publish only a fully validated matching plan. Start without a shared plan cache unless justified, avoiding cache-key and shared-cancellation complexity. | These illustrative caps are **unapproved and unmeasured**, not performance promises. A process-wide concurrency/admission limit and validation work units remain to be designed. Exact limits need numerical bounds and profiling; exhaustion and cancellation must fail without partial publication. Is a per-world uncached first implementation acceptable, and what target hardware and startup/memory budgets should guide the limits? |
| Authoring and compatibility | Extend the existing graph/settings and CPU preview with only implemented controls and diagnostics. Keep existing M4 assets usable and preserve absent/disabled cave output and identity. Keep runtime data independent of editor/render modules. | The owner's common game/mod graph direction remains; a reusable-subgraph/provider migration, C++ mod loading and retention policy are separate designs, not implied by this proposal. Is current M4 authoring integration acceptable for the initial cave stage while that migration is designed? |

## Before an algorithm or format is stable

Record each owner decision, the exact selected version, bounds, failure behavior and migration consequence. Specify seed bytes and reference vectors, candidate visitation and spacing, connectivity and tie rules, primitive interpolation, final-field/surface proof, pocket basis, conservative capsule and roof error margins, index bounds, checked arithmetic maxima, and measured resource limits. Unknown versions/providers and unsupported combinations must fail explicitly. The proposed default numbers above cannot be promoted into a saved-world promise merely by implementation.

M5 acceptance remains contingent on evidence that **every** planned route is capsule-walkable and that no unintended surface break occurs, with all enabled density-affecting stages included. Relevant independent reference, cancellation, seam, lifecycle, editor, game, cook, server and cross-host checks remain to be performed and recorded as applicable; an editor preview or single-host result is not proof of the complete contract.
