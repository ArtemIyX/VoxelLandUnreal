# 01 — World assets, runtime initialization, preview and cooked reconstruction

## Outcome and scope

Both `UVoxelLandFiniteWorld` and `UVoxelLandInfiniteWorld` are usable from the same game/graph workflow, in the editor, cooked game and a real dedicated server. The asset class chooses the world mode; there is no second editable mode switch. A finite world includes its bounded surface prepass and optional erosion; an infinite world generates requested regions locally, without a whole-world prepass. Both must eventually provide validated planned caves and optional pockets. A graph may be valid for one asset and invalid for another without changing the graph asset.

This plan depends on [02](02-mode-capability-enforcement.md), [03](03-remove-historical-paths.md), [04](04-infinite-world-streaming.md), and the route/field work in [05](05-cave-pocket-generation.md) and [06](06-final-mesh-route-certification.md). Share one authoritative preparation path; preview, cook and runtime must not independently reinterpret the same inputs.

## Baseline to reconcile

- The committed data module contains `UVoxelLandWorldDefinition`, `UVoxelLandFiniteWorld`, `UVoxelLandInfiniteWorld` and their separate settings/snapshot records under `Source/VoxelLandData/{Public/Data,Private/Data}`. Capture is game-thread-only and does not itself prove graph capability. Capturing parameterized graph functions is currently restricted.
- `Source/VoxelLand/Private/World/VoxelLandWorldSettingsInit.cpp` and `VoxelLandWorld.cpp` still initialize the old mixed M4 configuration/generator. Its job result and chunk workers are not yet an M5 plan/field barrier. `BeginPlay` is intentionally inert.
- Editor factory/action/validation files and changes to `VoxelLandEditor.cpp` and `VoxelLandWorldDefinition.cpp` were **uncommitted and interrupted** when this plan was authored. They include an unconditional cook-write guard and must be reviewed, reconciled and either completed or replaced; do not blindly overwrite them.
- `VoxelLandM5BoundBase` and `VoxelLandM5PlanPreparation` are fail-closed groundwork; they return `Unproven`, not an M5 generator. `VoxelLandGraphToolkit.cpp` still has an M4-oriented preview. Existing CPU-only work is not evidence of a real dedicated-server process.

## Integration progress

The current worktree adds mode-specific freshness checks after each reentrant function load, bounded material-path capture, control/function diagnostics, and metered built-in program loading for function inputs without copying tooltip text. The three-control diagnostic validator now lives in the runtime module and is shared by editor diagnostics. A separate worker-stage product loads all three built-in programs from one typed source, checks mode requirements, overrides and cooked curves, and retains the source and its supplied admission lease. That product does not validate provider work, backend suitability, descriptor identity or the final field and cannot authorize publication. The diagnostic compiler path is not a complete admission contract. The old M4 preview is not a preview of these typed assets. `InitializeFromWorldDefinition` and cooked writes remain fail-closed until the matching typed base, complete plan sets, final field and certificates exist.

## Execution, in dependency order

1. **Inventory and reconcile the worktree.** On the plugin's `VOXEL-5` branch inspect staged, unstaged, untracked and deleted files, including interrupted backend/test/editor changes. Record the plugin and outer project revisions. Read the current assets, `VoxelLandWorldDefinition.cpp`, `VoxelLandWorldSettingsInit.cpp`, `VoxelLandWorld.cpp`, `VoxelLandGraphToolkit.cpp`, `VoxelLandEditor.cpp`, current tests and this directory's plans. Preserve user content and unrelated edits. Decide which in-flight edits are usable before another agent touches their files.
2. **Establish one current contract.** Define separate Data-owned finite and infinite UObject-free snapshots and a tagged current world descriptor. Freeze source/function snapshots, cooked program/curve/provider dependencies, world kind, seed, units, graph revisions and all density-affecting finite/regional/cave settings. Add one enum/struct per dedicated file. Include an explicit derived mode: finite settings cannot contain an infinite region policy, and infinite settings cannot request erosion. Do not retain widget, actor, UObject or raw provider pointers in worker inputs. Do not add a parallel game-vs-mod graph asset.
3. **Capture and validate before dispatch.** On the game thread keep strong references while loading assets; copy bounded input and check revisions after every reentrant load. Route each of the three controls and the full dependency closure through the same world-target capability and program validation described by 02. Assign actionable errors for unsupported or missing providers, graph functions, invalid curves, out-of-domain demand and budget denial; keep invalid source editable and clear stale compiled data. Avoid an unbounded FText/soft-path rebuild masquerading as admitted work.
4. **Prepare immutable products off-thread.** Extend/refactor `VoxelLandM4Preparation` and world initialization into a result holding exactly one frozen descriptor and matching base generator, provider/module leases, finite grid/prepass lease where used, and the M5 planning service. Finite mode validates the *complete* domain/halo before allocating and runs global controls/erosion. Infinite mode creates no global grid: it starts bounded region preparation on demand. Charge real capture, program, prepass and worker costs as specified in 07; fail closed when no correct charge is available.
5. **Make initialization atomic.** Add explicit entry points accepting each asset (and the new current cooked descriptor) rather than silently translating it to an old M4-only request. Keep an initialization epoch, exact identity and consumer lifetime. Until base inputs, the complete relevant cave/region plan set, field/roof protection and route certificates match, publish no generator/chunk. On completion repeat source freshness and epoch checks after potentially reentrant actions. Failure, cancellation, shutdown and stale work preserve the last valid state but expose a clear error; never publish M4 terrain as a successful M5 world.
6. **Connect chunk generation.** Adapt the worker/scheduler in `VoxelLandWorld.cpp`, world state/jobs and demand logic to capture immutable plan-set and region leases. Generate baseline and cave samples via one common pipeline; include all intersecting region plans and halos. An M4-only `ClassifyChunkBeforeSampling` full/empty result is unsafe when caves/pockets are enabled: evaluate or use a proven bound, then classify and hash the final density. `VoxelLandDeterminism::HashDensity` can hash the fixed 35³ result; account its bounded scratch and check cancellation around it. Publish only when descriptor, epoch, ticket, plan-set generation and worker result still match.
7. **Unify preview with runtime.** In `Source/VoxelLandEditor/Private/Graph/VoxelLandGraphToolkit.cpp`, select either concrete world asset and capture the same snapshot. Use the same CPU preparation and sample pipeline, bounded 3D interior/cross-section views, seeds, entrance/route/roof/protection diagnostics and feature IDs. Keep prior preview explicitly stale during replacement/failure; camera/material/layout changes must not cause semantic replanning. Closing a toolkit must cancel/drain its own callbacks without affecting other editors or PIE worlds.
8. **Implement save, cook and restore.** Keep ordinary invalid graphs editable. Add type-aware `IsDataValid`, pre-save checks, current-format cooked graph/program/curve/descriptor data and reconstruct it without editor modules or runtime recompilation fallback. Use the actual cooker archive error path for invalid/unsupported data; remove the provisional unconditional cook rejection only after reconstruction succeeds. Test provider disappearance and unknown versions. Native object creation, reference ownership, undo/redo and save/reopen must use normal UE transactions/GC.
9. **Use correct lifecycle boundaries.** Each `UWorld` owns its cancellation token, plans and region consumers. EndPlay/shutdown cancel and drain that world's jobs and provider captures before releasing leases; one PIE world must not stop another. Module shutdown drains module-owned services without iterating or destroying actors. A dedicated server runs data-only CPU generation: no editor UI, render components, GPU requirement or Slate dependency.
10. **Remove superseded entry points** only after the new paths are in place; use 03 to delete old mixed assets and compatibility readers together with their callers. Do not remove unrelated assets or the valid deterministic identity/version checks.

## Tests and manual evidence

The human will build the actual editor/game/server targets and run M1–M5 suites separately, recording UE/compiler/OS/CPU/provider versions, revision and exit/log results. In Unreal: create both assets referencing the same graph; test valid and incompatible nodes, edit/undo/redo/save/reopen, preview finite erosion and infinite region movement, inspect cave entrances and stale-state behavior, start/stop two PIE sessions, then cook and launch game and real dedicated server. Record named seeds, assets, errors and screenshots. M4's deferred cook/server/cross-host/wider-world evidence is not already passed.

## Completion criteria and open decisions

- [ ] Both assets produce matching, fully initialized terrain through explicit manager calls; no `BeginPlay` generation or fallback.
- [ ] Preview, cooked reconstruction and game/server use the same mode validation and generation identity.
- [ ] Cook rejects invalid assets and successfully reconstructs valid assets without editor data.
- [ ] Per-world tasks/leases drain correctly; stale, failed and canceled work cannot publish.
- [ ] The human has recorded the specified automation, game, cook and real-server outcomes.

Decide exact public manager API, cooked asset payload ownership and finite/infinite world size defaults during integration; keep them documented and versioned. If provider metadata, reusable parameterized functions, field provenance or final certificates remain incomplete, report them as blocking success rather than replacing them with an unvalidated fallback.
