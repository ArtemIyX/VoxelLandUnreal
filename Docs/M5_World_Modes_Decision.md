# World modes: owner direction and implementation contract

The owner has directed VoxelLand to use **two world-settings asset types**: one for finite worlds and one for infinite-style worlds. The finite asset is the primary path for the owner's game and supports a bounded world-wide prepass, including erosion. The infinite asset targets games with an expanding, chunk-generated world and rejects graph nodes or stages that require a complete finite world. The owner confirmed that both settings assets use the **same terrain graph type**.

The owner also states that there are no old plugin users to migrate and directs removal of legacy compatibility. Therefore, historical readers, backend choices and saved-world identity branches that exist solely to preserve older development formats are not a product requirement. This does **not** mean deleting unrelated user-authored work, removing useful algorithms merely because of a name, silently corrupting files, or skipping format, provider and input validation. Replace old code with the selected current implementation, remove obsolete paths and tests deliberately, and report any development assets that need recreation. The current worktree and any uncommitted user changes must be preserved.

This decision supersedes the old-world preservation requirement in earlier M5 planning documents where it conflicts with the owner’s latest direction. The remaining M5 requirements—including connected planned caves and optional noise pockets in both modes, deterministic CPU generation, headless server support, walkability and no unintended surface breaks—are not relaxed. Nothing here claims the new assets, cave system, cook, server, cross-host or visual checks have been implemented or passed.

## Asset and compilation boundary

The two authoring assets should be separate concrete `UDataAsset` types, with common data and snapshot construction shared through an appropriate common base or composition. The finite type owns its finite world domain, global-control/prepass and erosion settings; the infinite type owns regional sizing, local generation and its bounded resource settings. The type itself selects the mode: do not expose an independent `bUnlimited` switch that can contradict the asset class. Both types may reference the same terrain graph, reusable subgraphs, material and common cave/capsule settings. A graph is not permanently marked invalid merely because it is incompatible with one asset: show a mode-specific diagnostic at the offending node/dependency, and permit it to be used by a compatible asset.

Compile and validate the *complete resolved graph* against the selected asset mode. This includes reachable subgraphs, expanded function calls, provider/operator dependencies, graph outputs, relevant world settings and stage ordering. A function cannot hide a forbidden global operation from an infinite asset. Diagnostics should identify the asset mode, node or function path and reason, and suggest the finite asset or a supported local alternative when one exists. A rejected graph must not leave previously compiled data usable as if it were current.

Use one shared capability-validation result in editor authoring, preview, save/cook and runtime initialization. The editor should surface incompatible nodes before a user attempts generation; cook must actually fail for an invalid asset, and a cooked or programmatically modified input must be revalidated at runtime. Unknown or missing provider capability information fails closed. A graph valid for the finite asset is not automatically valid for the infinite asset, even if it previously compiled successfully under finite settings.

## Capability contract

Classify operations by **their actual dependency footprint and execution requirements**, not simply by whether existing code calls a stage `Global` or `Sample`. Every built-in and registered provider needs an explicit, validated capability declaration or a compiler-proven equivalent; the declaration must propagate transitively through subgraphs and dependency edges. It should express at least:

| Capability | Finite world asset | Infinite world asset |
|---|---|---|
| Pure coordinate/sample operation with bounded inputs and a supported numeric backend | Allowed | Allowed when its coordinate precision and provider limits cover the requested samples. |
| Local operation with a finite, proven neighborhood or filter halo | Allowed if its footprint fits the world domain | Allowed if the entire halo can be produced from a bounded region dependency, independent of chunk generation order. |
| Bounded regional planning with deterministic ownership and boundary contract | Allowed where domain and budgets permit | Allowed; all required neighboring regions and shared boundaries must be resolved before dependent publication. |
| Whole-world aggregate, prepass, normalization or operation requiring every finite chunk/cell | Allowed only with an explicit finite domain, bounded work and memory | Invalid; report the responsible node/stage. |
| Unknown/unbounded footprint, missing provider metadata, unsupported backend, or unsupported stage ordering | Invalid until proved and supported | Invalid until proved and supported. |

The above describes semantic requirements, not a claim that the current graph compiler already provides these capabilities. A finite filter is not automatically incompatible with an infinite world: for example, the existing one-cell Smooth Density filter can be local if its complete deterministic halo is available. Conversely, moving a whole-world algorithm into a per-chunk call does not make it correct. The validity decision must include an operation's selected configuration: a provider with bounded and whole-world modes may be compatible only in its bounded mode.

### Current source inventory

- `UVoxelLandM4WorldConfig` currently combines both choices in one asset with `bUnlimited`, an `UnlimitedBackend`, finite grid fields and `bGlobalErosion`. Its capture rejects unlimited mode with global erosion. Replace that mixed authoring model with the two asset types and a common immutable runtime snapshot boundary.
- `EVoxelLandM4DomainMode` currently says `Finite`/`Unlimited`; `EVoxelLandM4UnlimitedBackend` currently distinguishes `LegacyFloat` and `FixedLattice`. The owner has removed a requirement to keep `LegacyFloat` as an old-world compatibility option. Select a current backend on demonstrated precision, determinism and supported-node merits; do not assume the existing fixed-lattice path supports every graph, or substitute a different noise basis silently inside one generated world.
- The experimental `EVoxelLandM4StageKind` describes `Global`, `Sample` and `Filter`, and `VoxelLandM4StageAnalysis` currently rejects Z for M4 global stages. This enum is not yet a complete capability contract. Some operations labeled global today are a finite implementation of an otherwise local coordinate field; conversely, a node's scope alone does not prove a finite halo, safe provider, or regional connectivity. Extend the real compiler/provider metadata and dependency analysis rather than inferring the decision from that enum alone.
- Existing `EVoxelLandOperatorStage` distinguishes `Sample` and `OneCellFilter`; the compiler treats `SmoothDensity` as the filter. Current built-ins include coordinate, arithmetic, SDF and 2D/3D noise operations plus `M4HeightOutput`. Their actual provider, dimensionality, backend and stage requirements must be checked from the compiled dependency closure. The current erosion controls are world-config/prepass settings, not proof that a standalone graph erosion node already exists.
- `VoxelLandWorldSettingsInit` currently prepares either a finite M4 prepass or an erosion-disabled unlimited generator. Editor preview routes through M4 preparation, and the config performs its own setting checks. The new assets must use a single mode-aware capability decision across all of these entry points, including cook and saved/cooked reconstruction.

## Mode-specific generation

**Finite:** capture an explicit half-open domain and require the complete control-grid, erosion, cave planning, filter, meshing and validation footprints to fit. Validate bounds, work and memory before global allocations. A complete immutable surface/prepass and a fully validated finite cave plan must be ready before matching chunks publish. Erosion is available here; its presence, graph inputs, domain and settings affect the current world identity.

**Infinite-style:** generate on demand from globally defined logical coordinates, immutable seed and graph/settings. There is no finite world-wide prepass or implicit global erosion. Pure and finite-halo stages must recompute the same global sample regardless of chunk, worker, request order or origin rebase. A finite regional cave plan is not a whole-world plan: assign coordinates with mathematical floor for negative values; derive each shared face portal from canonical neighboring region coordinates and immutable descriptor inputs; include full geometry, filters and meshing halos in dependency requests; validate both sides and reject missing or mismatched dependencies without publishing a partial result. Region admission and eviction must be bounded, retain active leases, and cancellation in one world must not cancel another. The owner has requested *both* regional planned networks and local noise pockets in this mode; reject/no-fallback behavior is a safety rule for failure, not a substitute for implementing them.

The term **infinite** is a product description, not a promise of literally unbounded machine integers or unlimited floating precision. Define and validate the supported logical-coordinate, voxel-size, provider, vertical-range and render/origin-management limits for the chosen current backend. Chunk and region identifiers, seeds and shared samples must be globally stable inside that supported domain. Never silently clamp, wrap or switch a backend when a limit is reached. The existing local-mode implementation and its `int32` chunk coordinates, fixed-lattice restrictions and rendering precision have bounded limits; wider world coordinates and origin management must be implemented and tested rather than inferred from the asset name.

Both modes keep workers UObject-free using captured immutable inputs; registry/provider lifetime must outlive their jobs. World initialization stays explicit, failure-atomic and world-local, and server execution must remain data-only. The final cave field, not just an ideal tunnel centerline, needs the approved capsule/roof/protection checks after all selected density-affecting operations and quantization. No local pocket may undermine that certificate.

## Implementation and evidence

1. Introduce the separate asset types and shared settings/snapshot contract; route every authoring, preview, cook and runtime entry through explicit asset-mode validation. Remove the obsolete mixed mode and historical compatibility code only after inventorying current references, without deleting user changes or examples.
2. Build an explicit capability model for built-ins, filters, finite prepasses and providers; validate the transitive graph/function closure. Test that an identical graph can be accepted or rejected according to the asset and stage configuration, including an incompatible node nested in a subgraph and an unknown provider.
3. Wire finite generation, erosion and validated planned caves; separately wire infinite local fields, bounded regional cave handshakes and pockets. Ensure both use the same final-field validation and appropriate CPU/server path.
4. Author meaningful independent tests for invalid capability and dependency cycles, finite boundary/halo errors, negative regional coordinates and shared portals, X/Y/Z seams, order independence, cancellation, lifecycle isolation, cook and stale-preview behavior. The owner will build and run automation/manual checks; no checks are represented as passed here.

Open engineering details include the final capability representation, exact infinite logical-coordinate limits, complete surface/capsule proof for arbitrary supported terrain, bounded process-wide admission, provider API, graph-function authoring/cook path and region-closure algorithm. They must be implemented or explicitly reported as unsupported; they are not permission to silently weaken the owner’s requested finite and infinite scope.
